## 〇、一句话结论

**v3 跑通了。** 拿到三样东西：① 72 个可以按名字解析的组件；② 其中 38 个组件的**精确实体数**（一共遍历了 378,942 个实体）；③ 12 张 API 注册表（系统 / 官方接口 / 静态目录 / 写命令）。

**但只答完了一半**：组件的"有哪些字段"没答完 —— 通用字段名试探只命中 1–5 个/组件，需要 v4 针对性补。同时意外挖出三条比预期值钱得多的能力（见第三节）。

## 一、怎么触发的（下次照做）

1. 部署 `world_probe.lua` v3 到 staging（Agent 可直接做，提升权限 + md5 双向核对）
2. **完全退出游戏再启动**（TPF2 只在启动时读 mod Lua，读档不会重载）
3. 进档，**让游戏真在跑**（1 倍速即可，不用加速）
4. Agent 发 `mcp__tpf2__get_game_state`（`force_refresh=true`）→ `world-probe.json` 从 187 B 变成 277 KB

**踩过的两个坑**（都已确认）：
- **游戏暂停 = 命令读不到**。轮询挂在引擎 `update` 回调上（`res/config/game_script/tpf2_mcp.lua:42`），暂停时模拟不步进，回调不来。
- **心跳不代表探针会跑**。`heartbeat.json` 每 ~2 秒自己写一次，但 `world-probe.json` **只在收到 `get_game_state` 命令时**才写。
- 自检办法：`bridge\heartbeat.json` 的 `last_update` 每 2 秒往前跳 = 轮询活着。

## 二、三条硬结论（都带数字）

### 2.1 `api.type.ComponentType` 确实不能用 `pairs()` 枚举

```
exists = true ;  value_type = table ;  pairs_members.count = 0 ;  first_pair_keys = []
```

**0 个成员**。所以 v2 的 `component_type_count: 0` 是必然的，不是写错了。这个组件表**只能按名字取**（`api.type.ComponentType["LINE"]`）。

### 2.2 命名规律 100% 成立（v3 的核心依据）

| 项 | 数字 |
|---|---|
| `api.type` 可枚举成员 | **205** |
| 由成员名推导出的候选组件名 | **205**（一个不漏） |
| **解析成功 = 真正的 ECS 组件** | **72**（35%） |
| 解析失败 | 133 |
| 策展名单额外贡献的新组件 | **0** |

策展名单一个都没多捞到 —— 说明「**组件名 = `UPPER_SNAKE(api.type 成员名)`**」这条规律没有一个例外。（唯一一个不在推导集里的候选是 `INFO`：`api.type` 里没有裸 `Info`，只有 `AircraftInfo` / `VehicleInfo` 这类。）

**解析失败的 133 个是什么**（分三类）：

| 类别 | 例子 |
|---|---|
| 写命令构造器（33 个） | `CREATE_LINE` `DELETE_LINE` `UPDATE_LINE` `SET_LINE` `BUY_VEHICLE` `SELL_VEHICLE` `SET_DATE` `SET_GAME_SPEED` `SET_NAME` `SET_COLOR` `CREATE_TOWNS` `REMOVE_TOWN` `DEVELOP_TOWN` `REPLACE_TERRAIN` `SPAWN_ANIMAL` … |
| 基础 / 数学类型 | `VEC2F` `VEC2I` `VEC3F` `VEC4F` `BOX2` `BOX3` `MAT4F` `ENUM` `VALUE` `REVISION` `SCRIPT_REF` `SCRIPT_PARAM` |
| 资源描述符 / 纯数据载体 | `TRACK_TYPE` `STREET_TYPE` `BRIDGE_TYPE` `TUNNEL_TYPE` `TRAFFIC_LIGHT_TYPE` `RAILROAD_CROSSING_TYPE` `SIGNAL` `MAP` `DATE` `*_INFO` `*_DATA` `*_DESC` `PROPOSAL*` |

→ **结论：能当"实体"遍历的只有那 72 个**，其余是接口、参数、资源定义。分不清这两类，就会白写一堆采集代码。

## 四、这一轮没答完的（v4 要补）

| # | 缺口 | 为什么重要 | v4 怎么探 |
|---|---|---|---|
| 1 | **`api.engine.transport` 的成员表** | 整个运输子系统，type=table 但没展开 | `safe_members(api.engine.transport)` |
| 2 | **`api.engine.terrain` 的成员表** | 地形 / 水体的读写入口 | 同上 |
| 3 | **`api.engine.system.<X>` 的方法表** | 31 个系统各自有什么方法 —— **拿精确数据的正路** | 对每个 system 做一层 `safe_members` |
| 4 | **`api.res.*Rep` 的方法表** | 不展开就不知道是 `get`/`getAll`/`getName` 哪种 | 对 15 张目录各做一层 |
| 5 | 🔴 **每个组件真正的字段名** | 通用试探名单命中率太低（多为 1–5 个） | 见下 |
| 6 | `api.util`（顶层）成员表 | 唯一没展开的顶层命名空间 | 一层 `safe_members` |

**关于第 5 项（最大的缺口）**，v3 摸到了两条线索：
- **`ASSET_GROUP` 暴露了引擎身份**：`__name = sol.ecs::component::AssetGroup`、`__index = table` → 引擎是 **Sol2 + ECS**，真实字段名可以从 `sol.ecs::component::*` 的命名里找，也可以从游戏自带的 Lua 源码里翻
- **`pairs()` 对所有组件都失败**（`pairs_ok=false`）→ 只能按名字逐个试读，这条路已经确定，没法绕
- 但**手写字段名是可行的**：现有 `vehicle.lua` 就是这么干的（`vehicle.config.capacities` 就是这么读到的），而 v3 的通用名单也抓到了 `transport_vehicle.config` / `town_building.town` / `transport_network.edges` / `base_node.position` / `person_capacity.capacity`
  → **v4 应该按组件分组各写一份字段名单**，而不是用一张通用名单打天下

## 五、对 v3 代码本身的修正意见

| # | 问题 | 建议 |
|---|---|---|
| 1 | **`TRAIN` / `RAIL_VEHICLE` / `ROAD_VEHICLE` / `SHIP` / `AIRCRAFT` 解析成功却没遍历** | 这五个比 `TRANSPORT_VEHICLE` 更有价值（能直接分车种）。车总量 664，代价可控 → **v4 必须遍历** |
| 2 | `WALK_LIST` 里没有 `TERRAIN_TILE` | 3136 个 heightmap tile 已知，可单独给个小预算探一次；现在只有同族的 `TERRAIN_TILE_HEIGHTMAP` 被遍历 |
| 3 | `SIGNAL` 不解析（只有 `SIGNAL_LIST`） | 452 个信号灯实体在 `SIGNAL_LIST` 里，说明信号是挂在 edge 上的列表组件，不是独立实体 —— 采集器要按这个结构写 |
| 4 | `component_walk` 里 `walk_budget` 字段丢了 | 部署版和我最后改的版本不一致（`total_entities_walked` 在、`walk_budget` 不在）→ 下次部署前先对一遍源码 |
| 5 | 通用字段名单 `PROBE_KEYS` 有 100+ 项 | 对每个组件都跑一遍，输出体积被 nil 撑大（277 KB 里大部分是 `{"type":"nil"}`）→ v4 应只保留非 nil 字段 |
