### 2.3 主因：**严重扎堆**（这是最关键的发现）

用车内时间统计**每个站的到站间隔**。先看**原始序列**（`Yangon` 与 `云浮` 在线路里**只出现一次**，不会被环线重复站污染）：

```
Yangon 到站间隔（秒）：
  102, 92, 44, 「1359」, 77, 259, 17, 「1308」, 68, 88, 18, 「1468」, 35, 94, 18, 「1464」, 64, 179, 19

云浮 到站间隔（秒）：
  115, 113, 73, 「1427」, 「1554」, 99, 97, 74, 「1350」, 101, 97, 73
```

**读法**：4 列车挤在约 **4 分钟内**相继过站，然后**空 22–26 分钟**（1,300–1,550 秒）没有一趟车，一小时内重复 4 轮。
**理想等间隔应为 407 秒**（单圈 1,628 ÷ 4）。现在是「4 列一起 → 空 23 分钟 → 4 列一起」。

| 车站 | 到站次数 | 间隔中位 | 最小 | 最大 | 最大/最小 | 理想值 |
|---|---|---|---|---|---|---|
| **Jeddah** | 32 | **97 s** | 42 | 790 | 18.8× | 407 s |
| **Yangon** | 20 | **94 s** | 35 | **1,468** | 41.9× | 407 s |
| **云浮** | 13 | 100 s | 73 | **1,554** | 21.3× | 407 s |

这正好解释了两件事：① 两列车 100% 满载、两列半空（挤在一起时前车吃满、后车吃剩）；
② 中位等待 11.5 分、94 人超 1 小时（等的就是那 22–26 分钟的长空档）。

### 2.4 次因：始发站装满 → 中途站上不去车

候车按**上车站**分布（20:05 采样）：

| 上车站 | 候车 | 车上（该站上车的乘客） | 占比 |
|---|---|---|---|
| **Yangon**（stop 3） | **729** | **0** | 40.2% |
| **Hanoi中央车站**（stop 2） | **622** | 100 | 34.3% |
| 中山西站（stop 1） | 453 | 273 | 25.0% |
| Jeddah（stop 0，始发） | 11 | 753 | 0.6% |

车在 Jeddah / 中山西 就装满了（列车12/6 达 100%），跑到 Yangon 时**已无座可上**——所以那两个站的队列越积越长。
**注意：这不是"总运力不够"，而是"运力被前段吃光 + 到站时间不匀"。**

## 三、判据：怎么算"达标"

用户给的标准是「**等待人数不超过站台最大限度**」。这里必须说清一个限制：

- ❌ **站台容量读不到**：`STATION_GROUP.capacity` 返回 `nil`，车站实体的可读字段只有
  `itemsLoaded / itemsUnloaded（累计上下客）/ cargoWaiting.PASSENGERS（当前候客）/ stations / position / name`。
- ✅ 所以用两个**可测**的替代判据：
  1. **候客是否持续上涨**（跨多次采样，像货运那条判据一样）——涨就说明服务不足；
  2. **你在游戏里读一次站台容量**（站台窗口显示的数字）给我，我把它设成警戒线，
     再用 `cargoWaiting.PASSENGERS`（已证实可读）做实时监控。

## 四、调整方案（按"先零成本、后花钱"排序）

### A. 求"均匀发车"——零成本，直击主因 ★建议先做

用 mod 自带的**相位控制器**（`APPLY_LINE_TIMETABLE` → `timetable_controller.lua`）给 JY 规定每个停站的发车时刻：

```
line_id = 98983
cycle_seconds = 1628                 # 实测单圈
epoch_game_time_ms = <当前游戏时间毫秒>  # 起算点
late_release_seconds = 30
stops = [
  { stop_index = 0, departure_offsets_seconds = [0, 407, 814, 1221], max_hold_seconds = 300 },  # Jeddah
  { stop_index = 3, departure_offsets_seconds = [0, 407, 814, 1221], max_hold_seconds = 300 },  # Yangon
  { stop_index = 1, departure_offsets_seconds = [0, 407, 814, 1221], max_hold_seconds = 300 },  # 中山西
]
```

原理：控制器在每个停站给每列车分配一个**发车时刻槽**，列车早到就扣住（`max_hold_seconds` 上限，带自动释放），
于是 4 列车被强制拉开成 0 / 407 / 814 / 1,221 秒的等间隔。

**预期**：到站间隔从「中位 97 s、最大 1,554 s」变成**约 407 s 均匀**；
两列吃满、两列空跑 → 变成四列各约 65–70% 载客；Yangon / Hanoi 不再被长空档饿着。

**前置**：① 写白名单加 `APPLY_LINE_TIMETABLE`（现在只有 `SET_LINE_STOP_POLICY`）；② **完全重启游戏**。
**⚠ 互斥**：一旦 JY 被运行图控制，就**不能再对它做临时扣车**（mod 会拒 `TIMETABLE_CONTROLS_LINE`）——
也就是说，如果以后要让 JY 给京广让路，就不能用这个方案控制 JY（二选一）。

### B. 换掉只有 146 座的那列车——一次性花钱，+23% 运力

列车21 是 CR400BF-C 编组，**只有 146 座**（其它三列各 576 座）。把它换成标准 8 节：
**+430 座**，车队容量 1,874 → 2,304（**+23%**），且不增加运行列数（间隔不变）。
> 若你是刻意留这个商务级编组，这条跳过。

### C. 直接加到 5 列——一次性花钱，+31% 运力

理想间隔 1,628 ÷ 5 = **326 秒**（比现在的 407 更密）。座位 2,304 → 2,880。
**但**：加车不解决扎堆，必须与 A 同做，否则新车也会被"带成一串"。

### D. 不做：压停站等待上限

京广那次已经证伪——**发车由"装载完成/装满"决定，`max_waiting_time` 不是约束**。
JY 的停站更长（`STOP`→下一站事件中位 118–285 秒，含区间运行），但那是装载本身占用的时间，压上限不会变快。

### E. 待查：与 JI线路 的分工

JY 与 JI 共用 5 段轨道（19.4 列/小时）。JI 是 50 km/h 的地铁，且**实载 91%**（两列都近满）。
如果 JI 也停 Jeddah / Hanoi / 广州北，短途客流可以改由 JI 承担、把 JY 的长途座位让出来——
**这条需要 OD 明细（各站对的起讫）来判定**，现有数据只能看到"上车站"，还需要"下车站"分布。
