# TPF2 客流核查与客运运力分析

日期：2026-09-27 ｜ 存档：`world-v1-3be64aa7d6888335915d90b1`（2.sav）｜ 全程只读，未向游戏写入任何内容

---

## 摘要（三句话）

1. **引擎的「吞吐量」不是客流**——实测 271 条线路，`吞吐量 = round(730.5 × 单车容量 ÷ 发车间隔)`，269 条精确吻合。它是**运力**（满载口径的理论年输送能力），不含任何需求信息。
2. **真实客流在这个 Mod 里读不到**：车辆装载、车站候客、分线收入/成本在引擎 API 中全部返回 `nil`（探针实测）。要拿真客流，只能在游戏内 UI 读（车站窗口的候客数、车辆财务图的收入）。
3. 因此**之前的"运量优先"结论需要降级为"运力优先"**；但走廊的时间占用、追及、单线判定、成本判定**不受影响**（那些不依赖该字段）。加车/拆编组对运力的精确收益已重新算出。

## 一、重大更正：`吞吐量` 是运力公式，不是客流

### 怎么发现的

先按"每车年运量"给线路排名，出现两个说不通的地方：8 条客运线算出的载客率全部 **>100%**（中位 200%、最高 250%），物理上不可能。于是反过来查这个字段到底由什么决定。

### 验证结果

对全部 271 条有车线路（含公路、水运、航空、云轨），计算 `吞吐量 × 发车间隔 ÷ 单车容量`：

| 指标 | 数值 |
|---|---|
| 拟合常数 K | **730.5** |
| `rate = round(K × 容量 ÷ 间隔)` 精确相等 | **269 / 271 条（99%）** |
| 残差 >1 的 2 条 | 中山面包转运、Jed燃料转运——车辆混编导致"平均容量"非整数，仍属取整误差 |

常数 730.5 = 2 × 365.25，即**引擎内部一年 = 730.5 个频率单位**（1 日 = 2 单位）。

**含义**：该字段可以被「车辆容量 + 发车间隔」完全推出来，所以它**不携带任何独立的需求信息**。它是这条线"满载时一年能运多少"——**运力供给**。

### 数据来源（可复现）

```
引擎字段：state.json → lines[].throughput = game.interface.getEntity(line).rate
          （原生 UI 同名「吞吐量」字段，与 API 一致——两边都是这个计算值）
车辆容量：state.json → vehicles[].capacity_total
发车间隔：state.json → lines[].frequency_seconds
复现：analyze_passenger.py（载客率自检）、analyze_passenger2.py（运力表）
```

### 更正后的全网口径（原值，不再乘站数）

| | 线路 | 车辆 | 年运力 | 每车年运力 | 占比 |
|---|---|---|---|---|---|
| **铁路** | 36 | 72（5.3%） | 30,143 | **419** | **26.1%** |
| 其他方式 | 237 | 1,296 | 85,397 | 66 | 73.9% |
| ↳ 铁路客运 | 8 | 29 | 6,132（人） | 211 | — |
| ↳ 铁路货运 | 28 | 43 | 24,011（件） | 558 | — |

**与旧报告对比**：旧数字"铁路 30.3% 运量、每车 1,366 vs 175"应改为**"26.1% 运力、每车 419 vs 66"**。方向不变（铁路单车运力效率仍是其他方式的 6.3 倍），但数字全部变了。

## 二、为什么拿不到真客流（证据链）

| 想读的东西 | 尝试的接口 | 结果 |
|---|---|---|
| 车站候客/待运量 | `STATION` 组件 `cargo` 字段 | 探针返回 `nil`（Mod 作者因原生崩溃禁用了 `game.interface` 车站采样） |
| 车辆实际装载 | `vehicle.getInfo()` 的 compartments / cargo / amount / load | 字段全部 `nil` |
| 线路收入/利润/成本 | `line.income / cost / profit / revenue` | 全部 `nil` |
| 运输历史 | `TRANSPORT_HISTORY` 的 revenue / profit / entries / cost | 全部 `nil` |
| 计划里的需求 | `line-timetable-plan.json → lines[].demand` | `sample_count: 0`，`onboard/waiting/load_factor` 为 null |
| 城镇人口 | `TOWN` 组件的 buildings / stations | 全部 `nil`（只有名字） |

实时帧（`operational-telemetry-vehicles_live.json`，每秒更新）里也只有位置/速度/停站序/门状态/发车倒计时——**没有任何装载字段**。

## 三、哪些旧结论作废、哪些仍成立

### 作废（曾在报告里写成"运量"）

| 旧表述 | 更正后 |
|---|---|
| "铁路用 5.3% 车辆做出 30.3% 运量" | 26.1% **运力** |
| "每车年运量 1,366 vs 175" | 每车年**运力** 419 vs 66 |
| "该加车的 7 条线（供不应求）" | 只是**运力配置**排名，不是需求排名 |
| "该减车 3 条（运力闲置）"：Yo木材 / 泉州钢铁 / 咸阳石化 | **作废**。运力配置低≠需求低，减车是纯赌 |
| "每车年运量是成本效益代理指标" | 只能当"运力/车"看；真实效益要看收入（游戏内读） |

### 仍成立（不依赖 `rate`）

- **走廊共用段时间占用 58.5%**、地铁车占 42.1%、慢车压快车 96 s —— 由几何 + 速度 + 间隔算出，与 `rate` 无关
- **相位锁定建议**（京广班次对齐 404 s 整数倍：808 / 1,216 s）
- **单线段判定**：45 段全部在站场咽喉（77–173 m），开放线上无长单线
- **成本判定**：复兴号 8 节约 $24,571/期运行费、16 节 $49,143；`qingguiCO` 21,600/节·期；零购置成本仅 JI线路 1 辆
- **B00220 区间已出现两车并发**（Yo木材 + 泉州钢铁）——这是观测事实，不是需求推断
- **京广客运通过的 4 个站不停**（见第六节）——实测行为

## 五、京广走廊：调车的运力效果（精确值）

| 线路 | 现状 | 加 1 列车后 | 运力变化 |
|---|---|---|---|
| **京广客运** | 1 列 16 节 / 1,294 座 / 17.9 分 | 9.0 分 | 879 → **1,758（+100%）** |
| **JY客运** | 4 列 8 节 / 468 座 / 6.7 分 | 5.4 分 | 847 → **1,059（+25%）** |
| **JI线路** | 2 列 6 节 / 318 座 / 5.7 分 | 3.8 分 | 675 → **1,012（+50%）** |

**京广客运 16 节拆成两列 8 节**：总座位不变（1,294），间隔 17.9 → **9.0 分**，年运力 **879 → 1,758（翻倍，不花钱）**。

这是当前最划算的一手：不动钱、不动轨道、运力翻倍、短编组起停更快（对共用段干扰更小）。

## 六、实测服务行为（68 分钟实采，1534 条事件）

数据源：`bridge/station-events.sqlite3`（`STOP` 停靠 / `PASS` 通过），覆盖 36 条铁路线、73 个车站、72 辆车。

| 线路 | 配置停靠 | 实测停靠 | **途经但不停** |
|---|---|---|---|
| **京广客运** | 3 站：天津、广州北站、Hanoi中央车站 | 3 站 ✓ | **Istanbul附站、Jeddah、中山西站、台北** |
| JY客运 | 10 项（7 个不同站） | 7 站 ✓ | — |
| JI线路 | 5 项（4 个不同站） | 4 站 ✓ | — |

**京广客运穿过 7 个车站，只服务 3 个。** 被跳过的 4 站里，Jeddah 由 JY客运 + JI线路 服务，中山西站由 JY客运 服务，Istanbul附站 和 台北 由 JI线路 服务——所以不是服务空白，但**京广客运本身在这些站吃不到客流**。要不要加停，取决于这些站的候客数（游戏内读）。

全网其余 PASS 热点：成都乘降所被成郑云轨内环通过 **122 次**不停（该线配置站里没有它）、Shanghai 22 次、Hanoi货物 12 次、西安货物 12 次、咸阳中央车站 9 次。

## 七、怎么把真客流测出来

**路径 A（推荐，今天就能做）——游戏内读数，给我数字我做分析**

需要读两类数，读一次即可，我来做供需匹配：

1. **车站候客数**：打开走廊上的关键车站窗口（广州北站、Jeddah、中山西站、台北、Istanbul附站、天津、Hanoi中央车站），记下**等待的乘客数**。
2. **车辆收入**：打开 3 条走廊线各一列车的财务图（京广客运的列车41、JY客运的列车12、JI线路的列车5），记下**年收入**（不用记成本，成本我已经从 .mdl 算出来了）。

有了这两组数，我就能算出：每条线**实际载客率 = 年收入 ÷ 票价 ÷ 座位数**、哪条线在排队、加车该加在哪。

**路径 B（低成本验证）——扩采样窗口**
`station-events` 每次只收 68 分钟。如果游戏连开 1–2 小时，事件样本会覆盖完整一个周转周期，能算出**每条线的实际发车间隔**（现在只有理论值），从而验证"班次"是否真的按配置在执行。

**路径 C（重量级，不推荐现在做）——解析存档**
`2.sav` 是 239 MB 的 zstd（magic `28 B5 2F FD`）压缩包，游戏内部序列化格式，里面可能有分线运输统计。需要先解压再逆向格式，工作量大、成功率不确定。**只有在前两条都不够用时才考虑。**

**Mod 层扩展不可行**：采集器的 Lua 已经在读 `STATION.cargo`，返回 `nil` 是引擎不暴露，不是 Mod 少写代码。

## 八、缺客流数据时的决策规则

既然客流读不到，把决策拆成"能定的"和"要先看数"的两类：

**可以直接做（不影响需求侧，纯改善）**

1. **京广客运拆两列 8 节**：运力翻倍、班次 9 分钟、不花钱 — 只在客流已经排到车装不下时才有意义，但代价接近零
2. **相位锁定**：京广班次由 1,076 s 调到 808 / 1,216 s（404 的整数倍），消除与 JY客运 的周期性撞车
3. **压停站等待上限**：三线现在都是 `max 180 s` → 地铁 30–45 s、复兴号 45–60 s
4. **让车规则**：慢车让快车（JI线路 50 km/h 让复兴号），别让复兴号在区间排队
5. **京广客运加停 Jeddah / 中山西站**（若要吃走廊中间站的客流；需先看这两站候客数）

**要先看数（游戏内读收入/候客后我再给结论）**

6. 三条线各加几列车
7. Yo木材 / 泉州钢铁 / 咸阳石化 是否减车
8. 广州北站（3 到发线，三线共用）是否扩容

**不要做**

- 不要为了"运量高"这个理由加车——那个数是运力，不是客流
- 不要在没看候客数之前减车
