## 二、"为什么慢"——把均速拆开

按轨道限速，14.6 km 跑 200 km/h 只需约 4.4 分钟；但计划单程 **999 s ≈ 16.6 分钟**（均速 52.6 km/h），
扣掉停站 77 s，运行 922 s → 运行均速约 57 km/h。

而实测在**移动状态下**平均 98.9 km/h、最高 162 km/h —— 说明：

1. **限速不是瓶颈**（路线是 200 km/h 级，观测段没有低速区间）；
2. 慢的原因是 **短站距 + 430 m 长编组反复起停 + 停站等待**：
   3 个停站把 14.6 km 切成 5–7 km 的短腿，长编组每次起停都要吃掉大量时间；
3. 计划里的区间运行时间（313/275/411 s）明显大于纯按限速推算的时间，
   这与运行图自身的声明一致——`limitations` 里写着
   *"Initial leg times are provisional until raw sectionTimes/lineStopDepartures are live-verified over multiple trips"*，
   也就是**这份运行图的时间还是保守初值**。

## 三、加车可行性：分四个维度

| 维度 | 结论 | 依据 |
|---|---|---|
| **需求** | ✅ 支持加车 | 每车年运量 2,637（铁路第一），班次 18 分钟偏长 |
| **通行能力** | ✅ 有余量 | 200 km/h 级轨道、闭区间占用率全网仅 4.9%、观测段 3.96 信号/km |
| **站点容量** | ⚠️ 受限 | 广州北站只有 **3 条到发线**，且它是全网 8 条线共用的枢纽；天津 4 条；Hanoi 6 条 |
| **混跑冲突** | ⚠️ 需错相位 | 与 JY客运 共用 2–3 条边，双方都在跑客运、速度等级接近（150–160），主要是**同时进出共用区间的排队问题** |
| **🔴 硬门槛** | ❌ 未验证 | **站台长度读不到**（`platform_length = null`），430 m 编组在三个站能否完整停靠**未经校验**；运行图因此把扩编/加车判为 `expansion_allowed = false` |

**结论**：加到 2 列车（班次 9 分钟）在需求与通行能力上没问题，
但必须先人工确认**三个站的站台长度 ≥ 430 m**、且**广州北站能同时容纳两列车**；
否则加了车也会在站台/咽喉处排队，反而把班次打乱。

> 关于你说的"低速车"：观测期间这条线上只有复兴号（16 节）在跑，
> **没有看到低速车占用本线**；与它共线的 JY客运 也是复兴号/CR200J 系。
> 如果你在游戏里看到本线被慢车压，很可能是**共用区间 `B00793` 一带**（JI线路 也在用）。
> 更省事的替代方案见下面第 4 条（拆编组）。

## 五、我能直接执行的操作（需要你先放行两道锁）

**当前状态：一道也执行不了。** 原因是 Mod 出厂配置里：

```lua
-- res/scripts/tpf2_mcp/config.lua
M.allow_write_operations = false
M.allowed_operations = {}
```

任何写操作都会返回 `WRITE_DISABLED`。要放行需要：

1. 新建 `res/scripts/tpf2_mcp/local_config.lua`（该文件**故意不随创意工坊包发布**，只能本地放），内容形如：
   ```lua
   return { allow_write_operations = true, allowed_operations = { SET_LINE_STOP_POLICY = true } }
   ```
   **改完必须完全重启游戏**才生效；
2. **关掉地图服务窗口**（`start_rail_map.bat` 那个黑窗）—— 因为 MCP 服务和它争同一个 bridge 邮箱锁；
3. 之后所有写操作走审批链：`get_operation_capabilities → propose_operation → validate_operation → create_task → plan_task → approve_task_step → continue_task → get_task`，**每次只执行一个变更**，你逐步点头。

**放行后我能执行的（Mod 已实现处理器的操作）**：

| 操作类型 | 作用 | 对应上面的建议 |
|---|---|---|
| `SET_LINE_STOP_POLICY` | 改停站策略：`max_waiting_time` / `min_waiting_time` / `load_mode` | #2 压缩停站时间 |
| `SET_LINE_STOPS` | 增删线路停站 | #4 调整站点设置 |
| `BUY_VEHICLE` | 购买车辆 | #1 / #6 |
| `ASSIGN_VEHICLE_TO_LINE` | 把车派到线路 | #1 / #6 |
| `SELL_VEHICLE` | 出售车辆（需精确确认串 `SELL_VEHICLE:<id>`） | #1 拆编组 |
| `APPLY_LINE_TIMETABLE` / `CLEAR_LINE_TIMETABLE` | 应用 / 清除线路运行图 | #3 |
| `HOLD_VEHICLE_AT_TERMINAL` / `RELEASE_VEHICLE_FROM_HOLD` | 把车扣在终端 / 释放（人工待避） | #5 的软性替代 |
| `CREATE_LINE` / `CREATE_LINE_FROM_SOURCE_ROUTE` / `RENAME_LINE` | 建线 / 改名 | — |

**我明确做不到的**（Mod 没有建造类操作，只能在游戏里手工做）：

- 铺侧线、加站台、延长站台（这是 #5、#7 的核心动作）；
- 修改轨道限速、增删信号机；
- 改变车站股道数。
- 另：`REMOVE_VEHICLE_FROM_LINE`（从线路上摘车但保留车辆）在项目文档里仍标注**不可用** —— 要减车只能用 `SELL_VEHICLE` 卖车。

## 六、我的建议顺序

1. **先做不需要花钱的两件事**：#2 压缩停站等待上限、#3 用实测时间重算运行图 → 班次和不稳定性立即改善；
2. **再确认站台长度**（#7）——这是加车与拆编组的前置条件，读不到就只能人工看；
3. **然后做 #1 拆编组重联**：同样 16 节车，拆成两列 8 节，班次直接翻倍，比花 $24.57M 再买一列更划算；
4. **最后才考虑 #6 直接加车**（站台确认可行后），以及 #5 的侧线/站台扩建（手工）。

## 七、数据边界

- 路线限速剖面来自**实测轨迹**（3 分钟采样，覆盖 23 条边 / 1.26 km），
  未覆盖区段不代表没有低速段；"路线是 200 km/h 级"这个结论只对观测段成立。
- 复线判断用几何平行边近似（中点 25 m 内、方向余弦 > 0.97）：全网检出 7,202 条平行边；
  本线观测段 70% 有平行邻边 → 其余 30% 需实地确认是站场咽喉还是单线区段。
- 站台长度、乘客等待、信号灯显示仍是 `UNKNOWN`（Mod 读取受限），
  因此"能否停靠 430 m 编组"与"需求是否满足"都只能间接推断。
